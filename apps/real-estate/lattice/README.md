## Running Locally

### With Python

```bash
./run.sh
```

The `run.sh` script invokes `python -m supero.cli`, which bootstraps your
app against the Supero platform. Each `./run.sh` run:

1. **Validates** project files (`schemas.py`, `setup.py`, `config.py`)
2. **Creates** a virtual environment at `.venv/`
3. **Installs** the Supero SDK
4. **Generates** `ui/index.html`, `ui/config.js`, `ui/server.py`
5. **Downloads** `ui/supero-ui.js` from CDN
6. **Bootstraps** the domain, schemas, users, workflows, and seed data via `setup.py`
7. **Runs** CRUD smoke tests against every schema
8. **Starts** the web server on port `5713`

**Stopping the server:** Press `Ctrl+C` in the terminal running `run.sh`.

### With Docker

```bash
docker compose up              # foreground
docker compose up -d           # background (detached)
docker compose logs -f         # tail logs
docker compose restart         # restart the container
docker compose down            # stop and remove container
```

The container runs the same `./run.sh` internally (when the default `CMD`
is in place), so each container start or restart re-runs the full bootstrap
sequence above. Your source files (`schemas.py`, `setup.py`, `config.py`,
`ui/`) are mounted as volumes in `docker-compose.yml`, so **changes are
reflected immediately** — no image rebuild needed for code edits.

**Rebuilding the image** is only needed if you change `Dockerfile` or
`requirements.txt`:

```bash
docker compose build --no-cache
docker compose up
```

### Useful CLI flags

```bash
./run.sh --setup-only       # Bootstrap without starting server
./run.sh --server-only      # Start server, skip bootstrap
./run.sh --reset            # Re-upload schemas and re-run bootstrap
./run.sh --docker           # Build and run with Docker Compose
./run.sh --no-interactive   # Use .env values without prompting
./run.sh --verbose          # Show detailed logs
./run.sh --skip-tests       # Skip CRUD smoke tests
```

### Bootstrap is idempotent

Re-running `./run.sh`, rebuilding the Docker image, or restarting the
container is **always safe**. The bootstrap step syncs schema and seed
data changes without duplicating records.

## Developing Your App

### The golden rule

> **All custom code goes in `ui/app.js`.** Never modify `supero-ui.js` — it
> gets overwritten whenever the SDK updates.

### Common extension patterns

| Goal | Hook | Complexity |
|------|------|------------|
| Add dashboard KPIs/charts | `dashboardExtras` | Low |
| Add detail view actions | `detailExtras` | Low |
| Declarative action buttons | `actionButtons` | Very Low |
| Custom card layouts | `customCards` or `cardTemplate` | Low–Medium |
| New pages/tabs | Add to `TABS` array | Low |
| Workflow triggers | `WORKFLOW_MAP` + `WorkflowTriggerButton` | Low |
| Full page replacement | Skip `AppShell`, build your own | High |

**See `CLAUDE.md`** for the complete API reference with code examples.

### Modifying the data model

1. **Edit `schemas.py`** — add or modify schema definitions
2. **Re-run** `./run.sh` (or rebuild your Docker container)
3. **Refresh your browser** — new fields auto-render in forms and cards

Schema changes are non-destructive by default.

### Adding workflows

Define workflows in `setup.py` → `WORKFLOW_DEFINITIONS`. Re-run `./run.sh`
to push them. Trigger from the UI:

```javascript
// Programmatic
services.workflow.run('workflow-id', { field1: value1 });

// Declarative (button in detail view)
var WORKFLOW_MAP = {
  'order': {
    workflowId: 'process-order',
    triggerLabel: 'Process Order',
    inputFields: ['order_number', 'customer_email']
  }
};
```

## Deploying to Production

Supero apps deploy to **any infrastructure you own** — there is no hosted
Supero runtime. You bring your own host.

### Path 1: Docker on a VPS / bare metal

```bash
# On your server
git clone <your-repo> lattice
cd lattice

# Create production .env (DO NOT commit this)
cat > .env <<EOF
SUPERO_DOMAIN=your-own-domain-name
SUPERO_PROJECT=lattice
SUPERO_API_KEY=ak_PROD_KEY_HERE
SUPERO_DEFAULT_TENANT=default-tenant
PORT=5713
EOF

# Start (runs in background, auto-restarts on reboot)
docker compose up -d
```

For production, **remove the volume mounts** from `docker-compose.yml` so
the image is self-contained.

### Path 2: Cloud platforms

Any platform that runs a Dockerfile works:

| Platform | Deploy command |
|----------|----------------|
| **Google Cloud Run** | `gcloud run deploy --source .` |
| **Fly.io** | `fly launch && fly deploy` |
| **Railway** | Connect repo, auto-detects Dockerfile |
| **Render** | Web Service → Docker runtime |
| **AWS App Runner** | Point at ECR image built from Dockerfile |
| **DigitalOcean App Platform** | Connect repo, select Dockerfile |
| **Heroku** | `heroku container:push web && heroku container:release web` |

For **all** of these: set your `.env` values as platform environment
variables (do **not** bake them into the image).

### Path 3: Static UI + serverless API proxy

Because `ui/` is pure static HTML/JS, you can split deployment:

- **Frontend** → Netlify, Vercel, Cloudflare Pages, S3+CloudFront
- **API proxy** → Cloud Run, Lambda, Cloudflare Workers

Update `ui/config.js` with your production API URL before deploying.

### Production checklist

- [ ] `.env` values set via platform env vars (NOT committed)
- [ ] `SUPERO_API_KEY` is a production key, rotated from dev
- [ ] Volume mounts removed from `docker-compose.yml`
- [ ] HTTPS enforced (via reverse proxy or platform default)
- [ ] Error monitoring enabled (Sentry, Rollbar, Datadog)
- [ ] Healthcheck endpoint responding on port 5713
- [ ] Container restart policy set (`restart: unless-stopped`)

## Troubleshooting

**"Domain not found" on login**
→ Check `SUPERO_DOMAIN` in `.env` matches your Supero dashboard.
  Re-run `./run.sh` to re-bootstrap.

**CORS errors in browser console**
→ You're hitting the API directly instead of through `server.py`.
  Load `http://localhost:5713`, NOT `file://` on `index.html`.

**Schema changes don't show up**
→ Re-run your start command to push schema updates. Hard-refresh the
  browser (`Cmd+Shift+R` on Mac, `Ctrl+Shift+R` on Windows/Linux).

**`supero-ui.js` missing or outdated**
→ Delete `ui/supero-ui.js` and re-run — the CLI will fetch the latest.

**Bootstrap fails with "API key invalid"**
→ Check `SUPERO_API_KEY` in `.env`. Keys must start with `ak_`. Regenerate
  from the Supero dashboard if needed.

**Docker: "port 5713 already in use"**
→ Stop the conflicting process or change the host port in
  `docker-compose.yml`: `ports: ["8080:5713"]`.

**Docker: container exits immediately**
→ Check logs: `docker compose logs app`. Most common cause is missing
  or invalid `.env` file.

**Docker: changes to `ui/app.js` not reflecting**
→ Volume mounts should make changes instant. Hard-refresh browser.
  Check you haven't removed the volume mounts from `docker-compose.yml`.

**Login works but no data appears**
→ Check browser console. Common causes: RBAC policy missing
  (check `setup.py`), tenant mismatch, or schemas not bootstrapped.

**CRUD smoke tests failing**
→ Run with `--verbose` to see the exact HTTP errors. Use `--skip-tests`
  to launch anyway, but fix the failures before production.

**AI assistant broke `ui/app.js`**
→ Restore from git: `git checkout ui/app.js`. Always make the assistant
  read `CLAUDE.md` first.

**`.supero-run.log` has the full history**
→ Every `./run.sh` invocation is logged. Check this file first when
  debugging any issue.
